# FastAPI Mastery Curriculum
This is the canonical catalog of **156 independently trackable learning units**. It separates HTTP, ASGI, Starlette, FastAPI, Pydantic, SQLAlchemy, PostgreSQL, Alembic, server, proxy, and application responsibilities instead of describing them all as framework magic.
- Choose a sequence in [LEARNING_PATHS.md](LEARNING_PATHS.md).
- Learn any unit earlier when useful; Codex gives a prerequisite bridge rather than blocking unnecessarily.
- Use one dedicated Worktree chat per learning unit.
- Create unit folders only when initialized.
## Canonical hierarchy

```text
Domain
└── Learning unit
    ├── Subtopic
    └── Evidence artifact
```
## Layer boundary map

```text
client → reverse proxy → ASGI server → ASGI middleware → Starlette routing
       → FastAPI dependency/parameter machinery → Pydantic validation
       → application service/domain work → SQLAlchemy/driver → PostgreSQL
       → response-model validation/serialization → middleware unwind → client
```
The same system branches differently on validation errors, dependency failures, application exceptions, rollback, streaming, cancellation, WebSockets, and background work. Those branches have owning units rather than one overloaded request-lifecycle chapter.

### Seniority evidence

**SDE-2 expectation:** independently implement, test, deploy, debug, and operate a bounded service or worker; own one contract; diagnose duplicate delivery, timeout, backlog, or rollout failures; and write a useful runbook.

**SDE-3 expectation:** lead boundary and migration decisions; coordinate cross-team contracts and compatibility windows; design reliability, security, observability, and incident strategy; quantify cost and operational load; and stop or reverse decomposition when evidence does not justify it.

## Completeness boundaries

The first 129 canonical units remain the approved FastAPI, HTTP, ASGI, Pydantic, database, migration, security, transport, testing, operations, and interview curriculum. The appended 27 `FAPI-MSV-...` units deepen those foundations into distributed-service decisions, RabbitMQ and gRPC correctness, cross-service consistency, resilience, observability, security, testing, evolution, incidents, and governance.

Completeness here means every major service-engineering boundary has a canonical owner. It does **not** mean every RabbitMQ policy flag, Kubernetes resource, Kafka operator, cloud queue product, service-mesh control plane, or provider-specific deployment option becomes a learning unit. Those remain examples, comparisons, experiments, or separate specialist curricula unless new independent evidence boundaries justify insertion.

The catalog also preserves stopping rules: a modular monolith, database-backed job table, managed queue, or ordinary HTTP call remains preferable when it satisfies the change pressure with lower operational and organizational cost.
